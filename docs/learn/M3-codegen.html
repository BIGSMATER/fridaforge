一、Go 语言轨道：模板引擎与资源嵌入

M3 引入 Go 的三个标准库概念：text/template（模板引擎）、embed.FS（编译时文件内嵌）、strings.Builder（高效字符串拼接）。组合使用它们可以构建出零外部依赖的代码生成器。

1.1 text/template — 数据驱动的文本生成

text/template 是 Go 标准库的模板引擎，核心思想：定义静态文本模板 + 注入动态数据 → 输出渲染文本。

package main

import (
    "os"
    "text/template"
)

type Person struct {
    Name string
    Age  int
}

func main() {
    // 定义模板 — 注意 {{ }} 内的 .Name .Age 是数据字段
    tmplStr := "Hello, my name is {{.Name}}. I am {{.Age}} years old."
    tmpl, _ := template.New("greeting").Parse(tmplStr)

    // 注入数据 — Execute 把渲染结果写到 io.Writer
    tmpl.Execute(os.Stdout, Person{Name: "BIGSMATER", Age: 28})
}
// 输出: Hello, my name is BIGSMATER. I am 28 years old.
模板核心语法
语法含义M3 中的用途
{{.Field}}注入字段值{{.ClassName}} → 类全限定名
{{if .Cond}}...{{else}}...{{end}}条件渲染判断 MethodSignature 是否为空
{{range .Items}}...{{end}}循环渲染无（M3 不做签名分割）

text/template vs html/template：后者会自动 HTML 转义（< → &lt;）。生成 JavaScript 代码必须用 text/template，否则 JS 语法会被破坏。

危险示范 — html/template 会毁掉 JS 
// 模板: "if (a < b)"
  // html/template 输出: "if (a &lt; b)" ← 语法错误！

1.2 embed.FS — 编译时文件内嵌

embed 包允许在编译时把文件目录"嵌入"到 Go 二进制中。生成的程序不需要任何外部文件。

package main

import (
    "embed"
    "fmt"
)

//go:embed data/*.txt
var staticFS embed.FS

func main() {
    // 从内嵌 FS 读取文件 — 跟 os.ReadFile 一样的 API
    data, _ := staticFS.ReadFile("data/hello.txt")
    fmt.Println(string(data))

    // 遍历内嵌目录
    entries, _ := staticFS.ReadDir("data")
    for _, e := range entries {
        fmt.Println(e.Name())
    }
}
//go:embed 规则
必须紧邻 var 声明，中间不能有空行
路径相对源文件所在目录
支持 glob：templates/*.js.tmpl
内嵌发生在编译期 — 运行时不可修改

1.3 strings.Builder — 高效字符串拼接

常规字符串拼接每次都分配新内存。 strings.Builder 内部用 []byte 缓冲，避免重复分配。

// ❌ 每次 + 都分配新内存
s := ""
for i := 0; i < 1000; i++ {
    s += "hello"
}

// ✅ Builder 只分配一次
var b strings.Builder
for i := 0; i < 1000; i++ {
    b.WriteString("hello")
}
result := b.String()

拼接 >10 次时 Builder 比 + 快 10–100 倍。

1.4 类型分发 — switch 语句

校验器需要根据 HookType 对不同字段做不同校验。Go 的 switch 不需要 break（自动隐含），多 case 用逗号并列。

这就实现了"Java 类型要求 ClassName，Native 类型要求 ModuleName"的差异化校验——同一循环，三条路径。

// 项目实际代码 — pkg/config/validator.go
switch h.HookType {
case spec.HookTypeOverload, spec.HookTypeOverride:
    if h.ClassName == "" {
        ve.Add(prefix+".class_name", "不能为空", 0)
    }
case spec.HookTypeNative:
    if h.ModuleName == "" {
        ve.Add(prefix+".module_name", "不能为空（native Hook 需要 module_name）", 0)
    }
default:
    ve.Add(prefix+".hook_type",
        fmt.Sprintf("不支持的值 %q，有效的 Hook 类型: overload, override, native", h.HookType),
        0)
}

1.5 map[string]int — O(1) 哈希去重

// 独立示例
func hasDuplicates(items []string) int {
    seen := make(map[string]int)  // key → 首次出现的索引
    for i, item := range items {
        if prevIdx, exists := seen[item]; exists {
            return prevIdx
        }
        seen[item] = i
    }
    return -1
}
// 项目实际代码 — pkg/config/validator.go
seen := make(map[string]int)
for i, h := range s.Hooks {
    dupKey := fmt.Sprintf("%s|%s|%s|%s",
        h.ClassName, h.MethodName, h.MethodSignature, h.HookType)
    if prevIdx, exists := seen[dupKey]; exists {
        ve.AddWarning(prefix+".hook_type",
            fmt.Sprintf("与 hooks[%d] 重复 ...", prevIdx), 0)
    } else {
        seen[dupKey] = i
    }
}

HashMap 查找 O(1) vs 二层循环 O(n²)：100 个 Hook 的重复检测，HashMap 只需 100 次比较，二层循环需要 4950 次。

1.7 ValidationError 的 Warnings 字段

设计关键：Warnings 不阻止生成，但需要通知调用者。

type ValidationError struct {
    Errors   []FieldError  // 阻止生成
    Warnings []FieldError  // 不阻止生成，但应展示
}

// 返回逻辑：
// HasErrors()            → 拒绝
// HasWarnings() + !HasErrors() → err != nil 但 Error() == ""
//   → 调用者需检查 ve.HasWarnings()

为什么返回 error 而不是 nil？ 调用者需要知道"有 warning"。Go 的 error 接口是最自然的传递方式——携带 Warnings 的 ValidationError 也是合法的 error 值。

1.8 Go 的 error 接口与自定义错误类型

Go 的 error 接口只有一个方法：

// 这就是标准库的 error 接口——完整定义
type error interface {
    Error() string
}

任何实现了 Error() string 的类型都是合法的 error。这意味着你可以创建携带结构化信息的错误：

// ❌ 字符串错误 — 机器无法提取信息
fmt.Errorf("template parse failed: %v", err)

// ✅ 结构化错误 — 可以通过 errors.Is / errors.As 精确判断
type TemplateError struct {
    Op   string  // "parse" 还是 "render"?
    Name string  // 哪个模板出错了?
    Err  error   // 原始错误是什么?
}

对比其他语言：Java/C# 用 try/catch + 异常类继承；Go 用返回值传递错误 + 接口统一。Go 的方式更显式——你无法"忘记处理"一个错误，因为它就是一个普通的返回值。

1.8.2 Unwrap() — 错误链的穿透

Go 1.13 引入 Unwrap() error 约定：如果一个错误实现了这个方法，errors.Is() 和 errors.As() 就能穿透错误链查找底层原因。

// 项目实际代码 — pkg/codegen/errors.go
func (e *TemplateError) Unwrap() error {
    return e.Err
}

// 使用方：
var te *TemplateError
if errors.As(err, &te) {
    fmt.Println("模板操作失败:", te.Op, "模板:", te.Name)
    // 还能拿到原始 text/template 的错误
    fmt.Println("底层原因:", te.Unwrap())
}
错误链类比：快递包裹 
外包装: "codegen: parse template 'overload.js.tmpl': ..."
  │ .Unwrap()
  ▼
内层:   "template: overload.js.tmpl:3: unexpected \"error\" in operand"
  │ .Unwrap()
  ▼
最内层: *text/template 的原始错误对象

——你可以精确地判断"是不是模板语法错误"（而非"是不是 IO 错误"），而不需要 strings.Contains 匹配错误文字。

1.8.3 项目实际代码

// pkg/codegen/types.go — 你写的代码
type GenerateOutput struct {
    Combined string            // 完整可执行 Frida JS 脚本
    Scripts  []GeneratedScript // 各 Hook 独立代码段
}

type GeneratedScript struct {
    HookTarget spec.HookTarget // 原始 Hook 目标
    JSCode     string          // 生成的 JavaScript 代码段
}

type RenderContext struct {
    AppPackage      string // 父级 HookSpec.AppPackage
    ClassName       string // 目标类名 (Java hooks)
    MethodName      string // 目标方法/函数名
    HookType        string // "overload" / "override" / "native"
    MethodSignature string // 参数签名整串 (空→无签名)
    ModuleName      string // Native .so 模块名
}

RenderContext 设计原则：它是一个扁平结构体——所有字段都是标量（string），没有嵌套对象。这是故意为之：text/template 的 {{.Field}} 语法适合扁平对象，嵌套会变成 {{.Nested.Field}}，增加模板复杂度。所以 HookTarget 的字段被"展开"成 RenderContext 的一级字段，外加 AppPackage（来自父级 HookSpec）。

// pkg/codegen/errors.go — 你写的代码
type TemplateError struct {
    Op   string // "parse" (编译) 或 "render" (渲染)
    Name string // 模板文件名 (如 "overload.js.tmpl")
    Err  error  // 底层 text/template 错误
}

type GenerateError struct {
    Op  string // "generate"
    Err error  // 底层错误
}

什么时候用 TemplateError vs GenerateError？

  • TemplateError：NewGenerator() 编译模板失败时 —— 这发生在程序启动时，是开发期 bug
  • GenerateError：Generate() 运行时遇到非法状态 —— 比如传入 nil HookSpec

两者都实现 Error() 和 Unwrap()——跟 M2 的 DeviceError/SessionError/ScriptError 一样的模式。这是项目中所有自定义错误的统一契约。

1.9 templates.go 项目代码 — embed + Parse + Execute 三件套

templates.go 是 //go:embed、template.ParseFS、ExecuteTemplate 三者首次组合使用。

// pkg/codegen/templates.go — 你写的代码

//go:embed templates/*.js.tmpl
var templateFS embed.FS

type Generator struct {
    tmpl   *template.Template
    logger *slog.Logger
}

func NewGenerator(logger *slog.Logger) (*Generator, error) {
    // 一次 ParseFS 编译所有模板 — 不用逐个 Parse()
    tmpl, err := template.ParseFS(templateFS, "templates/*.js.tmpl")
    if err != nil {
        return nil, &TemplateError{Op: "parse", Err: err}  // fail-fast
    }
    return &Generator{tmpl: tmpl, logger: logger}, nil
}

func (g *Generator) renderTemplate(ctx RenderContext) (string, error) {
    // 按 HookType 选择模板文件
    var name string
    switch ctx.HookType {
    case "overload": name = "overload.js.tmpl"
    case "override": name = "override.js.tmpl"
    case "native":   name = "native.js.tmpl"
    default:
        return "", &TemplateError{Op: "render", Err: fmt.Errorf("unknown hook type")}
    }

    // strings.Builder 作为 io.Writer — 模板直接写进去
    var buf strings.Builder
    if err := g.tmpl.ExecuteTemplate(&buf, name, ctx); err != nil {
        return "", &TemplateError{Op: "render", Name: name, Err: err}
    }
    return buf.String(), nil
}
设计要点
//go:embed templates/*.js.tmpl — 编译时 3 个模板文件嵌入二进制
template.ParseFS(fs, pattern) — 一次调用编译所有匹配模板
ExecuteTemplate(&buf, name, ctx) — 按模板名选择渲染，数据注入 RenderContext
strings.Builder 实现 io.Writer — 模板自然输出到缓冲区
switch ctx.HookType — 类型分发选择模板文件，跟 Phase 2 validator 一样
错误全用自定义 TemplateError 包装（Op/Name/Err）— fail-fast

二、Android 逆向轨道：Frida JS API 全景

M3 生成的是 Frida JavaScript 脚本。理解三种 Hook 模式对应的 Frida API 是正确生成代码的前提。

2.1 Java.perform — JVM 上下文入口

Java.perform(function() {
    // 此回调在目标应用的 JVM 线程内执行
    // 所有 Java.use() / Java.choose() 必须在此内部
    var System = Java.use("java.lang.System");
    console.log(System.currentTimeMillis());
});

为什么必须 Java.perform()？ Frida 的 Java bridge 需要 JNI 环境（JNIEnv 指针），而这个环境只在 ART 虚拟机线程中有效。Java.perform() 确保回调执行时 JNI 环境已就绪。

2.2 Java.use() + .implementation — Java 方法 Hook

Java.perform(function() {
    var Crypto = Java.use("com.example.Crypto");

    // overload 模式 — 拦截，但保留原方法行为
    Crypto.encrypt.overload().implementation = function(input) {
        var result = this.encrypt(input);      // ← 调用原方法
        return result;                          // ← 返回原结果
    };
});
overload vs override
overloadoverride
调用原方法this.method(args) ✅❌
原方法行为完全保留（只加日志）完全替换
返回值原返回值自定义

2.3 overload() — 方法签名匹配

Java 允许重载（同名多方法），Frida 用 .overload() 区分：

// 无参数 → 匹配第一个找到的同名方法
Target.method.overload().implementation = function() { ... }

// 有签名 → 精确匹配参数类型列表
Target.method.overload('java.lang.String', 'int').implementation = function(s, n) { ... }

M3 的 method_signature 字段整串原样注入——用户负责写 Frida 合法格式。

2.4 Interceptor.attach — Native 层函数 Hook

var module = Process.findModuleByName("libnative-lib.so");
if (module === null) {
    console.log("[-] Module not found");
    return;
}

var addr = Module.findExportByName("libnative-lib.so", "open");
if (addr === null) {
    console.log("[-] Export not found");
    return;
}

Interceptor.attach(addr, {
    onEnter: function(args) {
        // args[0] 是第一个参数 (ARM64: x0)
        console.log("[+] open() called, fd=" + args[0].toInt32());
    },
    onLeave: function(retval) {
        console.log("[+] open() returned: " + retval.toInt32());
    }
});

2.5 send() — 向宿主机发送结构化消息

Hook 执行在目标进程内。要把数据传回开发机，用 send()：

send(JSON.stringify({
    event: "method_enter",
    class:  "com.example.Crypto",
    method: "encrypt",
    args:   ["plaintext data"],
    timestamp: Date.now()
}));

2.6 HookType 三态设计

📍 Phase 2 内容
类型YAML 值Frida APIclass_namemodule_name
overload "overload" Java.use + .implementation + this.method() 必填 —
override "override" Java.use + .implementation（无原调用） 必填 —
native "native" Interceptor.attach — 必填
为什么 native 用 module_name 而不是 class_name？

Frida 的 Native Hook 定位函数需要两个关键信息：

  1. .so 文件名（Process.findModuleByName("libc.so")）
  2. 导出函数名（Module.findExportByName("libc.so", "open")）

Android 的 Java 类有包名体系（com.example.app），Native 库只有文件名（libnative-lib.so）。二者不能混用同一个字段。Phase 2 的 validator 通过 switch h.HookType 判断走哪条校验路径。

三、AI 编程范式轨道：代码生成器设计哲学

3.1 声明式 vs 命令式 — 为什么需要代码生成器

FridaForge 解决的核心问题：让人写声明（YAML），让机器写命令（JS）。

# 声明式 (YAML) — 用户写这个
hook_type: overload
class_name: com.example.Crypto
method_name: encrypt

↓ Generator.Generate() ↓

// 命令式 (Frida JS) — 机器生成这个
Crypto.encrypt.overload().implementation = function(input) {
    var result = this.encrypt(input);
    send(JSON.stringify({event: "enter", ...}));
    return result;
};

一条 YAML 膨胀为 10+ 行 JS。手写容易出错（忘 send()、忘 Java.perform、签名打错），代码生成器保证每个 Hook 遵循同一模式。

3.2 模板即契约

在 SpecKit 工作流中，模板（.js.tmpl）承担了"契约"角色：

spec.md          → 定义 WHAT（用户故事、功能需求）
plan.md          → 定义 HOW（架构、包结构）
data-model.md    → 定义实体映射
templates/*.tmpl → 定义 OUTPUT（How 的具象化）
tasks.md         → 定义 ORDER（逐步实现）

模板一旦写好，任何合法的 HookSpec 都能生成正确的 JS——YAML 就是正确答案的保证。

3.4 Semantic Versioning & Breaking Change

📍 Phase 2 内容

FridaForge 遵循 0.x.y 版本号，这一阶段允许 Breaking Change。

Phase 2 做了一个 Breaking Change：删除了旧的 hook_type: "replace"，重命名为 "override"。

Breaking Change： HookTypeReplace = "replace" → HookTypeOverride = "override"

测试文件中的 YAML 夹具从 hook_type: replace 改为 hook_type: override，常量从 HookTypeReplace 改为 HookTypeOverride。

不留别名，不搞 "deprecated 过渡期" — 0.x.y 阶段的特权。
