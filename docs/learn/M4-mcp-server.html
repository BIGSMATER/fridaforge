一、Go 语言轨道

1.1 encoding/json struct tag — 自定义序列化

Go 的 encoding/json 通过 struct tag 控制序列化行为。M4 中利用 json + jsonschema 双 tag 模式，让 MCP SDK 自动生成 Tool 的 inputSchema：

type GenerateInput struct {
    AppPackage string `json:"app_package" jsonschema:"目标应用包名,required"`
    ClassName  string `json:"class_name" jsonschema:"目标类全限定名,required"`
}

tag 写在反引号内，key:value 用空格或逗号分隔。json:"app_package" 控制 JSON 字段名，jsonschema:"描述,required" 让 SDK 生成 JSON Schema 的 description 和 required。

// pkg/mcpserver/types.go —— 项目实际代码中的完整双-tag 结构
type GenerateInput struct {
    AppPackage string `json:"app_package" jsonschema:"目标应用包名,required"`
    ClassName  string `json:"class_name" jsonschema:"目标类全限定名,required"`
    Signature  string `json:"signature,omitempty" jsonschema:"方法参数签名，仅 overload 时可选"`
    ModuleName string `json:"module_name,omitempty" jsonschema:"原生 .so 模块名，仅 native 时必填"`
}
omitempty tag：标记此 tag 的字段为零值时不会序列化到 JSON，保证 Tool 的 inputSchema 不会要求用户填写可选字段——JSON Schema 的 required 列表仅含非 omitempty 字段。

1.2 log/slog 结构化日志

Go 1.21 引入的 slog 替代传统的 log 包，支持键值对结构化输出：

logger := slog.New(slog.NewTextHandler(os.Stderr, &slog.HandlerOptions{Level: slog.LevelInfo}))
logger.Info("tool called", "tool", "spec_generate", "class", "com.example.Test")
关键约束：MCP stdio 模式下，stdout 仅用于 JSON-RPC 协议消息，日志必须走 stderr。

1.3 interface 注入模式 — 依赖解耦

依赖注入的核心思想：把"对象需要的东西"从外部传进去，而不是在内部自己创建。

// ❌ 硬编码依赖：Server 自己决定用什么 DeviceLister
type Server struct {
    lister *StubDeviceLister  // 写死了具体类型
}
func NewServer() *Server {
    return &Server{lister: &StubDeviceLister{}}  // 内部创建
}

// ✅ 依赖注入：调用者决定传什么进来
type Server struct {
    lister DeviceLister  // 依赖接口，不依赖具体类型
}
func NewServer(lister DeviceLister) *Server {  // 参数传进来
    return &Server{lister: lister}
}
三层价值——为什么用依赖注入？
  1. 方便测试：换一个参数就切换测试/生产模式，Server 内部代码一行不改。
    server := NewMCPServer(stubLister, ...) // 测试时注入假数据
    server := NewMCPServer(fridaLister, ...) // 生产时注入真实 Frida
  2. 隔离 CGO 污染：pkg/fridaengine 依赖 CGO，M4 用 interface 切断编译时依赖链，不 import fridaengine 就能编译运行。
  3. 独立演进：设备枚举的实现可以换成 ADB、Docker、模拟器——Server 完全不感知变化。
Go 的隐式 interface——与 Java 的关键区别

Go 不需要 implements 关键字。只要你有同名同签名的方法，就自动满足 interface：

// pkg/device/manager.go —— 定义 interface（接口方）
type DeviceLister interface {
    ListDevices(ctx context.Context) ([]Device, error)
}

// pkg/fridaengine/device.go —— 实现方（零声明，签名一致即自动满足）
type FridaDeviceLister struct { ... }
func (f *FridaDeviceLister) ListDevices(ctx context.Context) ([]device.Device, error) { ... }

// pkg/device/manager.go —— 另一个实现（同样零声明）
type StubDeviceLister struct { ... }
func (s *StubDeviceLister) ListDevices(ctx context.Context) ([]device.Device, error) { ... }
M4 的注入全景 
cmd/fridaforge/mcp.go —— 调用者负责创建依赖
  │
  ├── store := LoadMockStore("~/mock_devices.yaml")  ← 创建桩数据
  │
  └── NewMCPServer(
        store.DeviceLister,   ← 注入 DeviceLister interface
        store.ProcessLister,  ← 注入 ProcessLister interface
        slog.New(...),        ← 注入 slog.Logger
      )

Server 收到的都是 interface，不知道也不关心这些 interface 背后是真实 Frida 还是 YAML 文件。

1.4 go-sdk Tool 注册：泛型 + 反射协同模式

go-sdk 的 mcp.AddTool 同时使用了 Go 的两个高级特性：泛型（编译期类型安全）+ 反射（运行时自动生成 JSON Schema）。两者配合让 Tool 注册只需写 struct + handler。

泛型基础——同逻辑、不同类型，不复制代码：

// ❌ 每个类型写一遍
func AddInt(a, b int) int           { return a + b }
func AddFloat(a, b float64) float64 { return a + b }

// ✅ 泛型写一次
func Add[T int | float64](a, b T) T { return a + b }

[T int | float64] 叫类型参数列表。T 是占位符，int | float64 是类型约束。

AddTool[In, Out any]——两个类型参数，编译期验证签名：

// go-sdk 声明
func AddTool[In, Out any](s *Server, t *Tool, h func(ctx, ..., In) (..., Out, error))

// 调用——编译器自动推断：
mcp.AddTool(server, &mcp.Tool{...}, generateHandler)
//  generateHandler 签名 → In=GenerateInput, Out=GenerateOutput

// ❌ 类型不匹配 → 编译错误，不会留到运行时
mcp.AddTool(server, tool, func(ctx, req, string) (...) {...}) // In 推断为 GenerateInput ≠ string

反射基础——运行时读取任意类型的结构，go-sdk 通过它自动生成 JSON Schema：

func inspectStruct(v any) {
    t := reflect.TypeOf(v)        // 拿身份证
    for i := 0; i < t.NumField(); i++ {
        field := t.Field(i)
        field.Name                 // → "AppPackage"
        field.Tag.Get("json")      // → "app_package"
        field.Tag.Get("jsonschema") // → "目标应用包名,required"
    }
}
分工：泛型管编译期——签名校验、类型安全；反射管运行时——生成 JSON Schema、JSON 反序列化。两者配合让注册一个 Tool 只需写 struct + handler，三行代码。

项目实际代码——pkg/mcpserver/server.go：

func registerTools(server *mcp.Server, logger *slog.Logger) {
    mcp.AddTool(server, &mcp.Tool{
        Name: "spec_generate",
        Description: "根据 Hook 参数生成完整的 Frida JavaScript 脚本",
    }, generateHandler)  // 泛型推断 + 反射生成 schema

    mcp.AddTool(server, &mcp.Tool{
        Name: "spec_validate",
        Description: "校验 Hook 参数是否合法",
    }, validateHandler)
}

1.5 闭包捕获依赖——Go 的轻量 DI

问题：go-sdk 的 mcp.AddTool 要求 handler 签名固定，不能加额外参数。但 handler 需要访问 generator 和 logger。

答案：闭包——函数 + 它记住的外层变量。

从零开始：

// 第 1 步：普通函数——只用参数
func add(a, b int) int { return a + b }

// 第 2 步：函数内部定义函数
func main() {
    x := 10
    inner := func() { fmt.Println(x) }  // inner 用了外层的 x
    inner()  // 10
}

// 第 3 步：把内部函数返回出去——这就是闭包
func makePrinter(msg string) func() {
    return func() { fmt.Println(msg) }   // 记住了创建时的 msg
}
p1 := makePrinter("Hello")   // p1 记住 msg="Hello"
p2 := makePrinter("World")   // p2 记住 msg="World"
p1()  // "Hello"             ← 各记住各的
p2()  // "World"
关键：闭包记住的是变量本身（地址），不是当时的值。x := 10; f := func() { println(x) }; x = 20; f() 输出 20。

项目实际代码——pkg/mcpserver/server.go，每个 handler 是闭包，捕获外层 s *Server：

func (s *Server) registerTools(server *mcp.Server) {
    mcp.AddTool(server, &mcp.Tool{Name: "spec_generate", ...},
        // ──────────── 闭包开始 ────────────
        func(ctx, req, input GenerateInput) (*Result, GenerateOutput, error) {
            s.logger.Info(...)                       // ← s 来自闭包捕获
            output, err := s.generator.Generate(...) // ← 同上
            return ..., nil                          // 签名完全匹配 go-sdk 要求
        // ──────────── 闭包结束 ────────────
        })
}
对比三种 DI 方式
方式写法适用场景
全局变量var gen *Generator永远别用
构造函数参数NewMCPServer(gen, logger)Server 级别共用依赖
闭包捕获func(...) { s.gen.Generate() }Handler 级别，固定签名下间接访问
一句话：闭包就是让函数"私自带行李"——go-sdk 不让你加参数（行李不让带上飞机），但闭包把依赖藏进了函数内部。

三、AI 编程轨道

3.1 MCP 协议设计哲学

MCP 是 LLM 与外部工具之间的标准化接口协议。三个核心原语：

原语作用类比
ToolLLM 可调用的函数REST POST 端点
ResourceLLM 可读取的数据REST GET 端点
Prompt预定义的提示模板预设 prompt pattern

M4 仅实现 Tool 原语。Resources 和 Prompts 推迟到后续 Milestone。

3.2 JSON-RPC 2.0 消息格式

// 请求
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{...}}

// 响应
{"jsonrpc":"2.0","id":1,"result":{...}}

// 错误
{"jsonrpc":"2.0","id":1,"error":{"code":-32600,"message":"..."}}

// 通知（无 id）
{"jsonrpc":"2.0","method":"notifications/initialized"}

关键区别：请求有 id（需要响应），通知无 id（单向）。

JSON-RPC 2.0 标准错误码
Code含义
-32700Parse error — JSON 解析失败
-32600Invalid Request — 不是合法 JSON-RPC
-32601Method not found
-32602Invalid params
-32603Internal error

3.3 LLM 如何"理解" Tool

LLM 通过 Tool 的三个属性来理解如何调用：

name
唯一标识符（如 "spec_generate"），LLM 用字符串匹配选择 Tool
description
自然语言描述，LLM 判断何时使用
inputSchema
JSON Schema 结构化参数定义，LLM 构造调用参数
设计原则：一个设计良好的 Tool description 应该让 LLM 在 zero-shot 条件下（无示例）就能正确理解使用场景和参数含义。

3.4 MCP 基础知识与开发

MCP 是什么：LLM 和外部工具之间的标准化通信协议。类比 HTTP 是浏览器 ↔ 服务器的协议，MCP 是 AI 助手 ↔ 外部工具的协议。它解决的根本问题：AI 的训练数据是离线快照，无法访问你的本地工具、文件、API——MCP 让 AI 有了"手"。

三个原语：

原语做什么类比M4 实现？
ToolLLM 调用你写的函数REST POST✅ 4 个
ResourceLLM 读取数据REST GET❌
Prompt预定义提示模板快捷短语❌

Tool 的三要素：name（LLM 名字匹配）+ description（LLM 理解用途）+ inputSchema（LLM 构造参数）。LLM 看到这三个属性就能独立完成"什么时候用、传什么参数"的决策。

协议生命周期：initialize（握手）→ notifications/initialized（就绪）→ tools/call（操作）→ stdin close（关闭）。四步完成一次交互。

JSON-RPC 2.0 线格式——四种消息类型，靠 id 匹配请求和响应。请求有 id（需响应），通知无 id（单向）。

用 go-sdk 开发 MCP Server——最小完整示例 
// 第 1 步：定义 I/O 类型（jsonschema tag → SDK 自动生成 JSON Schema）
type Input struct {
    Name string `json:"name" jsonschema:"要打招呼的人名,required"`
}
type Output struct {
    Greeting string `json:"greeting"`
}

// 第 2 步：实现 handler（普通 Go 函数，SDK 负责 JSON↔Go 转换）
func handler(ctx context.Context, req *mcp.CallToolRequest, input Input) (
    *mcp.CallToolResult, Output, error) {
    return &mcp.CallToolResult{...}, Output{Greeting: "Hi " + input.Name}, nil
}

// 第 3-5 步：创建 server → 注册 Tool → 启动
server := mcp.NewServer(&mcp.Implementation{Name: "greeter", Version: "1.0"}, nil)
mcp.AddTool(server, &mcp.Tool{Name: "greet", Description: "打招呼"}, handler)
server.Run(context.Background(), &mcp.StdioTransport{})

3.5 opencode MCP 集成内部机制

第 1 步：opencode 连接 MCP 服务器——启动时对所有配置的 MCP server 调 tools/list，建立全局注册表 map[toolName]mcpServerConnection。

第 2 步：LLM 输出 function_call——不是 JSON，是结构化标记（Claude 用 tool_use content block，OpenAI 用 tool_calls）。opencode 内部的翻译层将其转换为标准 MCP 的 tools/call 请求，通过对应 server 的 stdin 发送。

第 3 步：Go 函数怎么变成 Tool——AddTool 在运行时"装箱"你的 handler：反射读 struct tag → 生成 JSON Schema；包装一层 JSON 反序列化 + 调用 + 序列化；存入路由表。之后 tools/call 到达时查表 → 反序列化参数 → 调用你的原始函数 → 序列化返回。

// go-sdk 内部的装箱逻辑（概念代码）
func AddTool[In, Out any](... ) {
    schema := reflectSchema(reflect.TypeOf(In))        // 装箱1: 反射→JSON Schema
    wrapped := func(req) {                              // 装箱2: JSON↔Go转换
        var in In; json.Unmarshal(req.Args, &in)
        return handler(ctx, req, in)                     // 装箱3: 调用你的函数
    }
    server.tools[name] = &tool{schema, wrapped}         // 装箱4: 存入路由表
}
完整链路：LLM 输出 function_call → opencode 查注册表找对应的 MCP server → 构造 tools/call JSON-RPC → 写 stdin → go-sdk 路由查表 → json.Unmarshal → 调你的 handler → json.Marshal → 写 stdout → opencode 读结果 → 还给 LLM
